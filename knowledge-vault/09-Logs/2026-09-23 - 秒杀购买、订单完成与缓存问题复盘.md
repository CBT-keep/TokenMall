# 秒杀购买、订单完成与缓存问题复盘

> **项目**：TokenMall 商城后端（Spring Boot 3.3.5 / Java 17 / MySQL / Redis / RabbitMQ / JMeter）
> **日期**：2026-09-23
> **关键词**：一键启动、JMeter、订单状态机、秒杀超卖、Redis Lua、Cache Aside、用户限购

---

## 一、今日目标

今天原本计划只做秒杀缓存和 JMeter 压测，但实际排查出了一条完整链路问题：

1. 桌面一键启动脚本看似执行了，实际没有正常进入 PowerShell。
2. JMeter 已安装，但需要生成可执行的 TokenMall 压测计划。
3. 订单支付成功后一直停留在“已支付”，无法进入“完成”。
4. 高并发秒杀出现严重超卖。
5. 秒杀用户限购每次都查 MySQL，第二次点击仍会走大量 SQL。
6. 秒杀活动缓存和秒杀记录缓存策略存在过度失效和一致性问题。

这次没有把秒杀整体切到 MQ/Outbox 异步模型，当前修复目标是先解决：

- 不超卖
- 用户不能重复购买
- 购买请求不再反复触发大量 SQL
- 支付成功后订单状态能正确完成

---

## 二、问题现象与根因

### 2.1 桌面一键启动脚本没有正常执行

现象：

```text
'-NoProfile' is not recognized as an internal or external command
```

根因：

`启动TokenMall.cmd` 和 `停止TokenMall.cmd` 当时是 Unix `LF` 换行。Windows `cmd.exe` 解析时把 `powershell.exe -NoProfile ...` 这一行拆坏了，实际没有进入 `Start-All.ps1`。

修复：

- 将 `.cmd` 文件统一改为 Windows `CRLF`。
- 增加 `scripts/dev/Start-MySQL.ps1`，MySQL 未运行时请求 UAC 启动。
- `Start-All.ps1` 改为只有 MySQL、RabbitMQ、Redis、前端都就绪时才打印 `TokenMall is ready`。
- `Stop-RabbitMQ.ps1` 改为幂等停止，并在没有 Erlang 节点时清理残留 `epmd`。

### 2.2 JMeter 已安装但没有可直接用的测试计划

安装位置：

```text
D:\JMeter\apache-jmeter-5.6.3
```

新增测试计划目录：

```text
perf/jmeter/
```

计划：

| 文件 | 用途 |
| --- | --- |
| `00-Smoke.jmx` | 登录、JWT、商品、购物车、账户、订单、秒杀列表冒烟 |
| `10-Browse-Read.jmx` | 商品浏览读接口压测 |
| `20-Login.jmx` | 登录和认证缓存压测 |
| `30-Seckill.jmx` | 动态注册用户并并发秒杀 |
| `40-Order-Functional.jmx` | 下单和模拟支付功能验证 |

期间还发现 JMeter GUI 只适合配置和小规模演示。高并发下 GUI 会先成为瓶颈，应该使用命令行模式：

### 2.3 订单状态无法进入“完成”

现象：

- 订单已支付：`status = PAID`
- 前端 Stepper 停在第 3 步“已支付”
- 第 4 步“完成”永远不亮

数据库证据：

```text
NULL -> PENDING_PAYMENT
PENDING_PAYMENT -> PAID
```

缺少：

```text
PAID -> COMPLETED
```

根因：

`PaymentService.mockSuccess()` 只调用了 `OrderService.markPaid()` 和 Token 发放，没有任何逻辑把订单状态改成 `COMPLETED`。前端映射本身正确，后端状态机缺少最后一个转移。

修复：

- 新增 `OrderService.markCompleted()`。
- Token 发放成功后调用 `markCompleted()`。
- 已有成功支付记录但订单仍是 `PAID` 时，重复调用支付接口会补做完成状态，避免重复发放 Token。

验证：

```text
FinalOrderStatus = COMPLETED
StatusLogs = PENDING_PAYMENT -> PAID -> COMPLETED
```

### 2.4 秒杀严重超卖

第一次高并发验证时发现：

```text
seckill_stock = 100
sold_count = 100
seckill_record = 343
本次测试成功记录 = 339
```

这不是“统计字段不准”这么简单，而是 100 份库存实际产生了 339 条成功记录。

根因：

购买逻辑是：

```text
先查活动
-> 判断 sold_count + quantity <= seckill_stock
-> 创建订单
-> activity.setSoldCount(...)
-> activityMapper.updateById(activity)
```

多个线程可以同时读到相同的 `sold_count`，然后各自执行 `+1`，最后互相覆盖。数据库唯一键 `uk_activity_user` 只能阻止同一用户重复，不能阻止不同用户超卖。

修复：

- Redis Lua 先原子预占用户标记和库存。
- MySQL 使用条件更新做最终扣减：

```sql
UPDATE seckill_activity
SET sold_count = sold_count + ?
WHERE id = ?
  AND deleted = 0
  AND sold_count + ? <= seckill_stock
```

- 影响行数为 0 时视为库存不足。
- Redis 用户 key 的 TTL 覆盖活动结束时间，并额外保留 24 小时。
- 购买失败时回补 Redis 库存并清理用户标记。

### 2.5 秒杀用户限购每次查 MySQL

原逻辑：

```java
Long existingRecord = recordMapper.selectCount(
        Wrappers.<SeckillRecord>lambdaQuery()
                .eq(SeckillRecord::getActivityId, activityId)
                .eq(SeckillRecord::getUserId, userId)
);
```

每次点击购买都会查询一次数据库。高并发下这只是“重复请求的额外压力”，而且不能解决数据库最终并发正确性。

修复：

- 使用 Redis key：

```text
mall:seckill:user:{activityId}:{userId}
```

- 用 Lua 原子判断用户是否已经参与。
- 只有 Redis 判断通过后才进入数据库流程。
- 数据库唯一键 `uk_activity_user` 继续作为最终兜底。

### 2.6 历史重复记录导致第二次点击仍走 SQL

现象：

用户已经有一条历史秒杀记录，但 Redis 用户标记不存在。第二次点击时：

1. Redis 预占库存成功。
2. 数据库唯一键拒绝插入 `seckill_record`。
3. 异常补偿把 Redis 用户标记删除。
4. 下一次点击又重复进入完整 SQL 流程。

修复：

- 捕获 `DuplicateKeyException` 后只回补 Redis 库存。
- 保留/补建 Redis 用户标记。
- 后续点击由 Lua 直接返回限购结果，不再进入数据库。

验证：

```text
第一次点击前：Redis 用户标记不存在
第一次点击后：Redis 用户标记存在
第二次点击日志新增：1 行认证日志
第二次点击 SQL：0 条
第二次返回：40006 超过购买限制
```

### 2.7 秒杀活动缓存过度失效

购买成功后调用：

```java
evictActivityCaches(activityId);
```

该方法会删除：

```text
mall:seckill:activity:{activityId}
mall:seckill:records:{activityId}
mall:seckill:list:
mall:seckill:list:all:
```

高频购买时，每次成功都会清掉全局活动列表和记录列表缓存，导致：

```text
购买成功
-> 删除列表缓存
-> 下一次查询回源数据库
-> 再次购买
-> 再次删除列表缓存
```

修复：

- 购买成功不再调用 `evictActivityCaches()`。
- 改为只清理当前活动详情和当前活动的记录缓存。
- 全局活动列表保持 TTL 自然过期，暂不因每次购买而失效。

如果后续要求活动列表销量实时精确，需要把销量拆成独立 Redis 计数器，而不是继续整体更新 JSON。

## 五、仍未完成的事项

1. **还没有接 MQ 异步秒杀**
   当前仍然在请求线程内同步创建订单，只是先用 Redis 把库存竞争挡掉。

2. **缓存更新仍在事务方法内**
   当前购买成功后会写结果缓存和清理部分缓存，但还没有放到事务提交之后。  
   后续应改成事务提交后更新缓存，避免回滚时 Redis 留下脏数据。

3. **历史活动 1 的超卖数据没有自动修复**
   当前修复只保证新购买不再超卖。已有 `seckill_record > stock` 的历史数据需要人工对账。

4. **全局活动列表的销量可能短暂不精确**
   为避免每次购买清空列表缓存，当前让列表缓存按 TTL 自然过期。  
   如果要求实时销量，需要把销量拆成独立计数器。

5. **Redis 库存 key 与数据库直接修改之间没有自动对账**
   如果直接改数据库 `sold_count`，需要同步清理 `mall:seckill:stock:{activityId}`。

6. **高并发 JVM 参数和 JMeter 发压能力还需要单独评估**
   当前压测已经有 200 线程成功验证，但正式压测建议使用命令行 JMeter，并记录 HTML 报告中的 `95% / 99%` 响应时间。

## 六、经验清单

1. Windows `.cmd` 文件必须使用 `CRLF`，否则 `cmd.exe` 可能拆坏 PowerShell 命令行。
2. 订单状态机必须显式定义和推进，前端 Stepper 只是展示，不会替后端补状态。
3. 秒杀防超卖不能依赖“先查询再更新”，必须使用原子条件更新或 Redis Lua。
4. Redis 用户限购 key 的 TTL 不能是固定 30 分钟，应该覆盖活动结束时间并留清理缓冲。
5. Redis 只是前置挡板，MySQL 唯一键和条件扣减仍然必须保留。
6. 缓存删除范围不能过宽。一次购买不应该清空整个活动列表缓存。
7. 高频写路径不要缓存完整实体再整体覆盖，库存/销量应拆成独立原子计数器。
8. 重复键异常不是“简单失败”：如果数据库已有历史成功记录，应补建 Redis 用户标记，避免下次再次查库。
