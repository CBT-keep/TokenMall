# Redis 缓存序列化问题复盘：商品详情接口第二次请求必炸

> **项目**：TokenMall 商城后端（Spring Boot 3.3.5 / Java 17 / Spring Data Redis + Lettuce）
> **日期**：2026-09-21
> **涉及文件**：`ProductService.java`（catalog 模块）、`RedisConfig.java`（common.redis 模块）
> **关键词**：Redis 缓存、GenericJackson2JsonRedisSerializer、DefaultTyping、Stream.toList、读写不对称

---

## 一、问题现象

商品详情接口 `GET /api/v1/products/{id}`：

- **第一次请求**：正常返回（缓存未命中，查数据库并回填缓存）
- **第二次请求**：HTTP 500（缓存命中，反序列化时抛异常）

异常信息：

```text
org.springframework.data.redis.serializer.SerializationException: Could not read JSON:
Unexpected token (START_OBJECT), expected VALUE_STRING: need String, Number or Boolean
value that contains type id (for subtype of java.lang.Object)
    at ...GenericJackson2JsonRedisSerializer.deserialize(...)
    ...
    at com.tokenmall.catalog.ProductService.detail(ProductService.java:90)
```

同时观察到 Redis 中的实际数据（关键线索）：

```bash
llen mall:sku:detail:101
# → 1（列表里只有 1 个元素）

lrange mall:sku:detail:101 0 -1
# → [{"@class":"com.tokenmall.catalog.dto.SkuResponse","id":1001,...}]
#   注意：唯一元素的内容是一段"数组"，而不是一个 SkuResponse 对象
```

---

## 二、根本原因

### 2.1 一条"读写不对称"的链路

```text
写入端：Stream.toList() 产出的不可变列表
    ＋ NON_FINAL 类型信息配置（RedisConfig）
    ↓
Jackson 跳过集合自身的类型信息 → Redis 里存的是"裸数组" [{...}]
    ↓
读取端：目标类型是 Object，序列化器要求数组必须带类型标识（["类型ID", 内容]）
    ↓
实际第一个元素是 { → 找不到类型 ID → 抛 MismatchedInputException
```

### 2.2 两个关键机制

1. **`Stream.toList()` 返回的是 JDK 不可变列表**（不是 `ArrayList`）。
   在 `ObjectMapper.DefaultTyping.NON_FINAL` 配置下，Jackson 序列化这种不可变列表时会**跳过集合自身的类型信息**，写进 Redis 的是没有任何类型标识的裸数组 `[{...}]`。

2. **读取时却强制要求类型信息**。
   反序列化目标为 `Object` 且开启了默认类型信息（default typing）时，序列化器遇到 `[` 开头的数据会当作"带类型信息的包装数组"解析，要求第一个元素必须是类型 ID 字符串（形如 `["java.util.ArrayList", [...]]`）。实际遇到 `{` 直接抛错。

一句话：**写入时丢了类型信息，读取时却要它。**

> 这是 Java 17 / Spring Boot 3 迁移后用 `Stream.toList()` 替换 `collect(Collectors.toList())` 时常见的 Jackson 已知坑。

### 2.3 为什么单个 Product 对象缓存一直没事？

`get()` 中缓存的 `Product` 是普通类（非 final），`@class` 被正常写入对象内部：

```json
{"@class":"com.tokenmall.catalog.entity.Product","id":104,...,"price":["java.math.BigDecimal",29.90]}
```

读取时自带类型线索，读写对称，所以正常。**只有"集合"走了那条丢类型信息的路。**

## 三、踩过的弯路（三次失败尝试）

| 版本 | 写法 | 结果 | 失败原因 |
| --- | --- | --- | --- |
| v1 | `opsForList().range()` + `JSONUtil.toBean(sku.toString(), ...)` | 炸 | 异常在 `range()` 内部反序列化阶段抛出，后面的转换代码根本执行不到 |
| v2 | `rightPushAll(skuKey, skus)` + `(SkuResponse) value` 强转 | 炸 | 同样炸在 `range()` 内部；且 `rightPushAll` 有重载陷阱，整个列表被当成 1 个元素存入 |
| v3 | `opsForValue()` 整体存取 + `instanceof List<?>` 过滤 | 还是炸 | `instanceof` 在 `get()` **成功返回之后**才执行，拦不住 `get()` 内部的序列化异常 |

**共同误区**：一直在改"读出来之后怎么处理"的上层代码，但异常发生在序列化器内部、`get()`/`range()` 返回之前——上层任何 `instanceof`、强转、`JSONUtil` 转换都执行不到。真正要解决的是**"写入的字节格式"与"读取时的期望格式"不匹配**的问题。

**附带的另一个坑：`rightPushAll` 的重载陷阱**

```java
redisTemplate.opsForList().rightPushAll(skuKey, skus);
```

`RedisTemplate<String, Object>` 有两个重载：

- `rightPushAll(K key, V... values)` → `(String, Object...)`
- `rightPushAll(K key, Collection<V> values)` → `(String, Collection<Object>)`

`List<SkuResponse>` 因泛型不变性**不是** `Collection<Object>`，第二个重载匹配不上；编译器选中 varargs 版本，把整个 `skus` 列表当作**一个 Object 元素**打包存入。表现为 `llen = 1`，且元素内容是一整个数组。

---

## 四、最终修复（4 个动作）

### 4.1 RedisConfig：`NON_FINAL` → `EVERYTHING`（根治）

`EVERYTHING` 是最全的类型信息策略，也是 Spring Data Redis 官方 `GenericJackson2JsonRedisSerializer` 的内部默认值：不管类型是不是 final、是不是不可变集合，都会写入类型信息。

```java
// 激活类型信息（写入 @class 字段），反序列化时才能还原成具体对象
// 使用 EVERYTHING：与 Spring Data Redis 官方默认一致，
// 避免不可变集合（如 Stream.toList() 的结果）、record 等类型丢失类型信息导致读取失败
objectMapper.activateDefaultTyping(
        objectMapper.getPolymorphicTypeValidator(),
        ObjectMapper.DefaultTyping.EVERYTHING,
        JsonTypeInfo.As.PROPERTY
);
```

### 4.2 写入端：`collect(Collectors.toList())` 替代 `Stream.toList()`（双保险）

```java
// 注意：不用 Stream.toList()（不可变列表），使用 collect 保证是可变 ArrayList，序列化时会正常携带类型信息
List<SkuResponse> skus = skuService.listByProduct(id)
        .stream()
        .map(skuService::toResponse)
        .collect(Collectors.toList());
```

### 4.3 读取端：`allMatch` 防御校验（健壮性）

```java
Object value = redisTemplate.opsForValue().get(skuKey);

// 缓存命中，且元素类型正确时才返回；否则视为未命中，重建缓存
if (value instanceof List<?> list && !list.isEmpty()
        && list.stream().allMatch(SkuResponse.class::isInstance)) {
    List<SkuResponse> skus = list.stream()
            .map(SkuResponse.class::cast)
            .toList();
    return ProductDetailResponse.from(product, skus);
}
```

缓存里若出现不认识的格式，视为未命中重建，而不是静默返回空 SKU 列表。

### 4.4 一致性：更新/删除时清缓存

```java
public Product update(Long id, ProductRequest request) {
    Product product = get(id);
    apply(product, request);
    productMapper.updateById(product);
    // 更新后清除缓存，避免读到旧数据
    evictCache(id);
    return product;
}

public void delete(Long id) {
    get(id);
    productMapper.deleteById(id);
    // 删除后清除缓存，否则仍能从缓存查到已删除商品
    evictCache(id);
}

/**
 * 清除商品详情与 SKU 列表缓存
 */
private void evictCache(Long id) {
    redisTemplate.delete(List.of(
            RedisKeys.PRODUCT_DETAIL + id,
            RedisKeys.SKU_DETAIL + id
    ));
}
```

### 4.5 清理 Redis 脏数据

旧格式（裸数组）数据无法被新代码读取，必须删除：

```bash
DEL mall:sku:detail:101
```

> 商品缓存 `mall:product:detail:*` 不用清：Product 是非 final 类，新旧配置下格式一致，兼容。

## 六、经验清单

1. **排查缓存问题，先看 Redis 里实际存了什么**（`GET` / `LRANGE` 看原始字节），对比"写入预期 vs 实际格式"，比盯着 Java 代码猜快十倍。本次就是"元素内容是个数组、`llen=1`"这条线索锁定了整条因果链。
2. **报错发生在序列化器内部时，上层代码怎么改都没用**——要解决"数据格式与序列化器期望"的匹配问题。
3. **缓存场景慎用 `Stream.toList()` / `List.of()` 等不可变集合**，优先 `collect(Collectors.toList())` 或 `new ArrayList<>(...)`。
4. **对象缓存优先用官方默认的 `EVERYTHING` 类型信息策略**；`NON_FINAL` 会静默跳过 final 类型（record、不可变集合等）的类型信息，是隐蔽的坑。
5. **`instanceof` / 强转等防御只作用于"反序列化成功之后"**，不能拦截序列化器内部异常。
